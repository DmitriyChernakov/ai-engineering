
## Что это

_Агент_ — это цикл: модель получает задачу → решает, какой инструмент вызвать →
инструмент выполняется → результат возвращается модели → модель отвечает
или вызывает следующий инструмент. 
Формула: **Agent = LLM + Tools + Loop**.

## Зачем это нужно

LLM сама по себе не может выполнять действия в реальном мире: искать в интернете,
считать, читать файлы. Инструменты дают ей «руки», а цикл — возможность повторять,
пока задача не решена.

---
# Ключевые идеи из **[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)**

1. Принципиальная разница между _Workflow_ и _Agent_ заключается в том, кто управляет потоком выполнения: в _Workflow_ он задан кодом, а в _Agent_ LLM сама динамически принимает решения и выбирает инструменты. При этом автономность агентов ведет к каскадному накоплению ошибок, поэтому их оправданно применять только для задач, где невозможно заранее прописать четкий алгоритм.
2. Augmented LLM - это LLM, усиленная дополнительными возможностями: извлечение информации, инструменты, память. Она является атомарным строительным блоком, из которого собираются абсолютно все архитектуры: как workflows, так и автономные агенты.
3. Anthropic советует начинать с простого, так как добавление многоуровневой агентности ведет к росту стоимости, задержек и каскадному накоплению ошибок, что сильно усложняет отладку. Сложные системы стоит внедрять только тогда, когда простое решение не справляется с задачей.

# ТЕСТЫ
## Прогон 1:

 Системный промпт:
```
SYSTEM = """tools:
1. search_web(query) — поиск информации
2. calculate_number(expression) — калькулятор
3. get_time - часы

Если нужен инструмент, ответь в JSON в формате:
{"action": "tool", "tool": "имя_инструмента", "args": {"параметр": "значение"}}

Если инструмент не нужен, ответь в JSON в формате:
{"action": "answer", "text": "ответ пользователю"}"""
```

Ответы агента:
```
============================================================
Тест 1: Инструмент calculate_number
============================================================
Вопрос пользователя:
Посчитай 900 * 600

Ответ модели:
{"action": "calculate_number", "args": {"expression": "900 * 600"}}


Ответ пользователю: Результат умножения 900 на 600 равен 540000.
============================================================
Тест 2: Инструмент search_web
============================================================
Вопрос пользователя:
Найди информацию про Python 3.12

Ответ модели:
{"action": "search_web", "tool": "search_web", "args": {"query": "Python 3.12"}}

[Агент выбрал инструмент: search_web({'query': 'Python 3.12'})]
[Результат: Результаты поиска по запросу 'Python 3.12': Python 3.12 вышел в октябре 2023]

Ответ пользователю: {"action": "answer", "text": "Python 3.12 вышел в октябре 2023 года."}
============================================================
Тест 3: Инструмент get_time
============================================================
Вопрос пользователя:
Сколько времени?

Ответ модели:
{"action": "get_time", "text": ""}


Ответ пользователю: Время сейчас: {"action": "get_time", "text": ""}
============================================================
Тест 4: Инструмент не нужен
============================================================
Вопрос пользователя:
Привет, как дела?

Ответ модели:
{"action": "answer", "text": "Привет! Я виртуальный ассистент и всегда настроен чтобы помочь. Как могу вам сегодня помочь?"}


Ответ пользователю: Привет! Я виртуальный ассистент и всегда готов помочь. Как сегодня можно вам помочь?
============================================================
Тест 5: Попытка сломать инструмент calculate
============================================================
Вопрос пользователя:
Подели 10 на 0

Ответ модели:
{"action": "answer", "text": "Деление на ноль не определено"}


Ответ пользователю: Деление на ноль не определено.
```

## Наблюдения 

Тест 1: Очень редко агент формирует JSON нужного формата. В значение для ключа action сразу подставляет имя инструмента, из за чего инструмент не используется, и конечный ответ отличается от ожидаемого. Пробовал разные варианты и пользовательских и системных промптов, нет никакакой корреляции.

Тест 2: Всегда выбирает необходимый иструмент и дает корректный ответ.

Тест 3: Инструмент не был выбран ни разу. Аналогичная ситуация с тестом 1 - не формирует JSON нужного формата в 10 из 10 случаев.

Тест 4: Отрабатывает корректно, выбирает обычный ответ пользователю.

Тест 5:  Также успешен, сломать не удалось, модель понимает базовые правила математики.

Возможно была выбрана неудачная структура JSON контракта, а в силу того, что модель не самая сильная, она путается и совершает ошибки.

---
## Подводные камни

- Слабые модели (7B) плохо следуют сложным многоуровневым контрактам. Чем проще формат, тем надёжнее.
- Непоследовательное описание инструментов в промте (где-то скобки, где-то нет) приводит к тому, что модель не распознаёт инструмент.
- `format="json"` в Ollama форсирует JSON всегда, даже когда нужен текст. Конфликт между промтом и параметром.
- Контракт «простой» ≠ «примитивный». Одна лишняя абстракция = каскад ошибок.
